Findings C — Critical: crashes and dead forms

C1 · Dashboard 500s once you own a subscription Critical DONE · slice 1

Adding your first subscription bricks the home page. app.py imports set_setting but the dashboard tile calls get_setting("fortnightly_income")NameError on every dashboard view while any active subscription exists. Reproduced: login → GET / raises; the full traceback ends at app.py:285.

app.py:12 (import) vs app.py:285 (use) · guarded only by if subs: at app.py:275, so zero-subscription users never see it — which is why CI and staging stayed green.

Recommend: add get_setting to the database import (one word). Then add a dashboard-with-subscriptions test — the gap is coverage, not architecture.

C2 · Fortnightly Budget page 500s on every load Critical DONE · slice 1

The route passes date objects as start/end; the template's nice_date filter feeds them to parse_date → strptime(date_obj) → TypeError. The page has never rendered for anyone. Reproduced: GET /subscriptions/fortnight raises.

routes/subscriptions.py:284-290 (passes dates) · app.py:100-104 (filter assumes strings) · templates/subscriptions/fortnight.html:10.

Recommend: harden nice_date to accept date objects (fixes every future caller too), or pass .isoformat() in the route. Same one-test fix as C1: GET the page in pytest.

C3 · Bank CSV form can't be submitted; BankSync card nested inside it Critical DONE · slice 1

The NetBank form opens at line 33 and is never closed — no submit button, no </form> — and the entire BankSync card (its own <form>) sits inside it. Nested forms are invalid HTML: browsers merge or drop the inner form, so "Sync now" can POST to the wrong route (which then flashes "Choose a CSV file"). NetBank CSV import is unreachable from the UI it was built for. Verified: 4 <form opens vs 3 closes on the rendered page; no submit control in the bank-card segment.

templates/spend/import.html:33-71.

Recommend: close the bank form with its own submit button ("Import bank CSV") before the BankSync card opens. Route-level tests passed because they POST directly — add one test asserting the rendered page contains both submit targets.

C4 · Add-subscription page 500s: csrf macro never imported Critical DONE · slice 1

Found by the new smoke test, same class as C1/C2: subscriptions/form.html calls {{ csrf() }} but only imports form_errors from _macros.html — UndefinedError on every GET of the add/edit page. Fixed by adding csrf to the import; covered by the smoke sweep going forward.

templates/subscriptions/form.html:2 vs :15.

Recommend: done — no further action; the smoke test owns this class now.

Findings H — High: wrong numbers and one-way doors

H1 · Fortnight "Groceries (planned)" is the whole plan's cost High DONE · slice 2

subscription_fortnight totals the entire plan range and labels it this fortnight's groceries. A 4-week plan doubles the apparent fortnight spend and halves the "Spare" figure — the exact number the page exists to show. The dashboard tile repeats the same unscoped total.

routes/subscriptions.py:264-284 → services/budget.py:59-72 · app.py:280-284 (dashboard tile).

Recommend: prorate by plan days overlapped with the fortnight, or label honestly ("whole plan ≈ $X over N days"). Prorating is ~5 lines with the existing date_range overlap.

H2 · Paused and deleted subscriptions are unrecoverable High DONE · slice 3

Delete and Pause do the identical thing (active = 0); the list shows only active = 1; "N paused subscription(s) hidden" has no link, no restore, no true-delete. The Toggle button always reads "Pause" though the route also reactivates — a path no UI can reach. Purging history to fix a typo'd subscription is impossible.

routes/subscriptions.py:192-223 · templates/subscriptions/list.html:57-80.

Recommend: a "Paused" section (or filter tab) listing inactive subs with Resume + Delete-forever; make Delete confirm it hides rather than removes, or split the actions for real.

H3 · Suggestion engine's bank half can never fire High

The suggest page and its "How suggestions work" card promise BankSync-based detection, but banksync_unclassified is read from settings and never written anywhere — the sync path renders unclassified rows on a result page and drops them. Purchase-history suggestions work; the bank half is documentation for a feature that doesn't exist.

routes/subscriptions.py:306 (sole reference) · templates/subscriptions/suggest.html:63-72.

Recommend: persist the sync's unclassified rows to that setting (cap the list, e.g. last 200) — the reader and matcher already agree on shape (description/amount). Until then, cut the BankSync bullet from the explainer.

Findings M — Medium: friction and mistrust

M1 · "Marked as paid" lies when a bill is several cycles overdue Medium DONE · slice 3

advance_next_due adds exactly one frequency to the stored date. Pay a bill that's 3 months late and the flash claims success while the bill still shows as due. The catch-up logic already exists (next_occurrence walks forward to ≥ today) — mark-paid just doesn't use it.

services/subscriptions.py:161-169 vs 97-109 · routes/subscriptions.py:236-243.

Recommend: advance from max(next_due, today), or reuse next_occurrence; flash the new due date (already done) and, when catching up multiple cycles, say so.

M2 · Accepting a suggestion always assumes "due today" Medium DONE · slice 3

subscription_accept_suggestion hardcodes next_due = today. For a charge detected mid-cycle (or a yearly bill spotted from last quarter's bank line), the first due date is wrong on arrival. The purchase detector already computes the cadence internally but doesn't return the last-seen date the route needs.

routes/subscriptions.py:350-351 · services/subscriptions.py:285-335 (dates computed, not returned).

Recommend: return last_seen in the suggestion dict and default next_due = last_seen + frequency, still editable on the add form (which the accept path currently skips — consider landing on the form prefilled instead of one-click create).

M3 · Import-page copy describes two import paths; there are now four Medium

"CSV files import immediately with no review" sits next to a bank-CSV flow whose whole point is review-before-force-import, and the sidebar CSV-format card doesn't mention bank CSVs or BankSync at all. A careful user following the copy will be surprised twice.

templates/spend/import.html:17, 73-90.

Recommend: one line per path with its review behaviour (invoice → review; order-history CSV → direct; bank CSV → review; BankSync → auto + review). Cheap, high-trust.

M4 · Suggestion cards show raw frequency codes Medium

Suggestions print {{ s.frequency }} raw ("monthly") while the list and fortnight pages format it ("Monthly"). Same data, three casings across three pages.

templates/subscriptions/suggest.html:42 vs format_frequency (list.html:55, fortnight.html:89).

Recommend: use the shared format_frequency in the suggest template.

M5 · Bills vs Subscriptions: the feature has two names Medium

Top nav says "Subscriptions", the mobile bottom nav says "Bills", the pages mix both ("Subscriptions & Bills", "Fortnightly Budget"). Users searching settings or help for either term find half the feature.

templates/base.html:33 vs :116.

Recommend: pick one ("Bills" matches the mental model — rent and electricity aren't subscriptions); keep the other as a subtitle.

Findings L — Low polish

L1 · Suggestion scan window starts at a hardcoded 2024-01-01 Low

Fine today, silently wrong in a year (stale one-off charges re-qualify as "recurring"). Derive it from the newest purchase minus ~13 months.

routes/subscriptions.py:301.

L2 · Fortnight groceries always render in danger-red Low DONE · slice 2

text-danger is unconditional on a neutral number — red reads as "over budget" even when spare is healthy. Tie the class to the summary tone.

templates/subscriptions/fortnight.html:37.

What's working (don't regress)

Empty states with next actions

Subscriptions list and Suggestions both explain the void and link the fix (add manually / import data). The best onboarding in the app.

Subscription forms keep input and show inline errors

The add/edit routes re-render with typed values — the B1 pattern from round 1 was actually applied to the new code. Hold this as the template.

API key show-once + prefix + last-used

The full key displays exactly once, the table keeps an identifying prefix, last-used timestamps on first call. Correct secrets UX.

Duplicate review before force-import

Bank result page lists possible duplicates with checkboxes instead of silently importing. Right trust model — once C3 lets users reach it.

Process finding: the safety net has a hole shaped like pages

CI runs the full pytest suite plus a Docker build whose smoke test hits only /health. C1 and C2 are one-line mistakes that any authenticated GET of the affected page would catch — but no test GETs the dashboard with subscriptions present, or the fortnight page at all. The suite is 441 green and both pages 500.

Recommend: a test_smoke_pages.py that logs in and GETs every blueprint index (dashboard, plan, list, pantry, spend, subscriptions ×4, settings, fortnight) with minimal seed data, asserting 200. ~30 lines, catches this entire class forever. Extend the Docker smoke test past /health the same way.

Roadmap (impact first, shippable slices)

  1. Hotfix: unbreak the money pages. C1 (one import), C2 (template pass), C3 (filter hardening + page tests). Half a day; everything else depends on these pages existing.
  2. Make the numbers honest. H1 prorating + L2 tone class. Same area, same tests.
  3. Close the subscription loop. H2 paused-management UI, M1 catch-up mark-paid, M2 prefilled accept. The feature becomes trustworthy.
  4. Wire suggestions to the bank feed. H3 persistence + M4/M5 copy and naming consistency. The advertised feature becomes real.
  5. Page-level smoke coverage. Process fix so round 3 isn't this report again.
